## 구현 메모
- 변경한 파일: `functions/src/index.ts`, `functions/package.json`, `functions/README.md`, `firestore.rules`, `firebase.json`, `apps/web/src/features/workspace/`, `apps/web/src/features/auth/AuthApp.tsx`, `apps/web/src/services/firebase.ts`, `apps/web/scripts/verify-workspace.mjs`, `verify-auth.mjs`, `verify-firebase.mjs`, `README.md`, `docs/03-data-model.md`, `docs/06-security-testing.md`, 이 문서와 패키지 설정.
- 의사결정 및 이유: 워크스페이스 생성은 Firestore 규칙이 검증하는 3문서 일괄 쓰기로 처리하고 초대 메일과 분리한다. 멤버십 문서 ID는 UID이고 목록용 미러를 함께 기록한다. 초대는 Admin SDK 함수에서 이메일 주소 전용, 7일 만료, 32바이트 무작위 토큰의 SHA-256 해시만 저장한다. 수락은 확인된 로그인 이메일 일치와 초대 상태를 서버 트랜잭션에서 검증한다. 로컬에서는 링크를 반환하고 로그에 출력하며 실제 환경에서는 SMTP 비밀값으로 메일을 발송한다.
- 예외 상황·권한·로딩 검토: 비로그인·이메일 미확인·장 외 초대·잘못된 이메일 주소·토큰 오류·이메일 불일치·만료·철회·재사용·동시 수락을 차단한다. 클라이언트에서 초대 문서를 직접 읽을 수 없고, 워크스페이스·채널·업무는 멤버만, DM 원문은 참여자만 읽는다. 최초 공간 생성 외 클라이언트 쓰기는 차단한다.
- 발견한 문제/해결: 실제 프로젝트에는 Functions가 배포되지 않아 기존 `createWorkspace` 호출이 실패했고, 공통 오류 문구가 이를 초대 메일 실패로 잘못 표시했다. 생성을 초대 함수와 분리하고, 실패 문구도 생성 전용으로 바꿨다. 생성 규칙을 실제 프로젝트에 배포했다. 실제 초대 메일에는 여전히 Blaze 요금제와 SMTP 설정이 필요하다. Functions 에뮬레이터가 생성한 초대 링크는 기본 `localhost:5173`이며, 웹 화면에서는 현재 접속 포트로 바꿔 열도록 했다.
- 추가 개선: 초대 대상의 Gmail 제한을 없애고 모든 형식에 맞는 이메일 주소를 허용한다. 사이드바 관리 메뉴는 장에게만 표시하고, 메인 관리 화면에서 멤버와 초대 현황을 확인한다.
- 관리 화면 정리: 상단에 멤버 초대와 새 워크스페이스를 2열로 놓고, 아래에 초대 현황과 멤버 목록을 각각 전체 폭으로 배치한다. 헤더의 워크스페이스 선택 목록과 사이드바·스크롤바를 어두운 테마에 맞췄다.
- 다음 일차에 넘길 사항: 실제 메일 발송 설정과 초대 Functions 배포가 남았다. Firestore 규칙은 실제 프로젝트에 배포했다. 채널·메시지·업무 쓰기 경로는 해당 일차에 서버 검증을 추가한다. 채팅·업무 화면은 여전히 샘플 데이터다.

## 포트폴리오 기록
- 문제 정의: 인증만으로는 워크스페이스 소속을 증명할 수 없으며 초대 링크의 중복 사용이나 DM 원문 접근을 막을 서버 권한이 없었다.
- 선택한 접근과 대안: 워크스페이스 생성은 규칙으로 검증하는 일괄 쓰기, 초대와 멤버 수락은 호출형 함수로 나눴다. Firestore 규칙은 생성 외 클라이언트 쓰기를 차단한다. 별도 초대 코드 입력 대신 이메일 전용 링크를 사용했다.
- 검증 근거(수치 임의 생성 금지): `npm run test:workspace`로 이메일·비밀번호/Google 계정의 독립된 장 생성, 초대 없는 단독 문서 생성 차단, 초대 발급·철회·수락, 이메일 불일치, 미확인 계정, 만료·재사용·동시 수락과 멤버·비회원·DM 참여자 읽기 권한을 확인했다. `npm run test:auth`에서 가입 후 워크스페이스 생성 경로를 확인했다. 실제 프로젝트에는 Firestore 규칙 배포가 성공했으며 실제 메일 수신과 Functions 배포는 검증하지 않았다.
