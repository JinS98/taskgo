## 구현 메모
- 변경한 파일: `functions/src/taskResponses.ts`, `functions/src/taskModel.ts`, `shared/contracts/src/task.ts`, `apps/web/src/features/tasks/TaskBoardPanel.*`, 에뮬레이터·브라우저 검증 스크립트와 정책·데이터 모델·README.
- 의사결정 및 이유: 검수 미선택 업무는 담당자가 `IN_PROGRESS → DONE`으로 완료하고 `NO_REVIEW`를 남긴다. 검수 대기 업무는 요청자가 승인(`APPROVED`) 또는 2~1000자 사유로 반려한다. 반려 시 `REWORK`, 재제출 시 `REVIEW_PENDING`으로 옮기고 회차를 올린다.
- 발견한 문제/해결: 기존 제출 뒤 요청자가 응답할 수 없었다. 서버의 역할·상태·입력 검증과 보드 액션을 연결하고, 반려 사유를 업무 카드·이력에 표시한다. 모든 전이는 업무 문서와 이력 이벤트를 한 트랜잭션으로 기록한다.
- 검증: 타입 검사·린트·웹/Functions 빌드, 에뮬레이터의 빈/긴 반려 사유·권한·중복 승인·완료 사유 테스트, 두 Chrome 계정의 반려→재제출→승인 및 검수 없는 완료 흐름을 통과했다.
- 다음 일차에 넘길 사항: 24일차 근무시간·공휴일 계산 후 제출·재제출 시 정확한 검수 기한 저장. 예약 알림과 자동 완료는 이후 일정에서 연결한다.

## 포트폴리오 기록
- 문제 정의: 업무를 검수 대기 상태로 제출할 수 있었지만 요청자가 승인·반려하거나 담당자가 재제출할 수 없었다.
- 선택한 접근과 대안: 클라이언트의 직접 쓰기를 허용하지 않고, 기존 서버 함수에 역할별 상태 전이와 이력 기록을 확장했다.
- 검증 근거(수치 임의 생성 금지): 중복 승인 2건 중 1건만 성공했다. 브라우저 두 계정에서 반려 사유 표시, 검수 회차 2, 최종 `DONE`과 `APPROVED`를 확인했다.
