## 구현 메모
- 변경한 파일: `apps/web/src/features/chat/LiveChatPanel.tsx`, `messageHistory.ts`, `useRoomHistory.ts`, `useLiveChatStore.ts`, `apps/web/scripts/verify-live-chat.mjs`, README와 소켓·아키텍처 문서.
- 의사결정 및 이유: 오프라인에서 소켓을 끊고 전송을 비활성화한다. 온라인 복귀 시 토큰 인증과 룸 참가를 다시 거친 뒤 Firestore 서버에서 최신 페이지부터 이미 확인한 메시지까지 조회한다. 캐시만 읽으면 오프라인 동안 저장된 메시지를 놓칠 수 있다. `messageId`·`clientMessageId`로 합쳐 중복 표시를 막는다.
- 발견한 문제/해결: 첫 30개 페이지보다 많은 누락 메시지가 생기면 단일 페이지 조회로는 복원되지 않는다. 재조회 중 재연결이 겹친 경우 조회 완료 후 다시 읽도록 했고, 확인된 메시지는 늦은 ACK 타임아웃으로 실패 표시되지 않게 했다. 일시적인 룸 참가 오류와 재연결이 멈춘 경우 재시도한다.
- 검증: `npm run test:live-chat`에서 두 Chrome 세션 중 하나를 오프라인으로 두고 다른 쪽에서 메시지 35개를 전송했다. 복귀 후 35개가 각각 한 번씩 나타났고, 오프라인 중 작성한 초안과 복귀 후 전송을 확인했다. 기존 채널·DM 과거 내역, 페이지네이션, 스크롤 복원, 재입장 검증도 통과했다. `npm run typecheck`, `npm run lint`, `npm run build:web` 통과.
- 다음 일차에 넘길 사항: 16일차의 타이핑·접속·실패·재시도 상태 UX. 실제 배포 환경 검증은 별도 진행이 필요하다.

## 포트폴리오 기록
- 문제 정의: 실시간 연결이 끊긴 동안 받은 메시지는 소켓 이벤트만으로 복원할 수 없다.
- 선택한 접근과 대안: 복귀 후 서버 저장 내역을 페이지 단위로 재조회하고 기존 메시지와 병합한다. 소켓 재연결만 기다리거나 캐시 내역만 사용하는 방식은 누락분을 보장하지 못한다.
- 검증 근거(수치 임의 생성 금지): 브라우저 통합 테스트에서 오프라인 동안 메시지 35개를 보냈고, 복귀 화면에 35개가 중복 없이 표시됐다.
